一、产品概述

1.1 我们为什么做这个产品

如果你问一个在读硕士或博士「最近在忙什么」，十有八九会得到三个答案：

  • 在整数据。 仪器导出的表格乱七八糟，缺值、重复、单位不统一，得一行行收拾，再反复画图返工。
  • 在找论文。 在好几个数据库之间来回切换，下载几十篇 PDF，读完发现只有三四篇真正有用。
  • 在写论文。 中文意思要翻成「学术英语」，格式要按期刊模板一点点调，参考文献要一条条核对。

这三件事合起来，往往占掉科研人员一半以上的时间——但它们本身并不直接产生新知识。

更麻烦的是，这三件事各有各的工具，彼此不通：数据在 Excel / SPSS / Origin 里，文献在 EndNote / Zotero / 知网里，写作在 Word 里。中间的搬运全靠人工复制粘贴，数据一改，图和文全得重来。

与此同时，擅长读写文字、识别图片的 AI 已经足够好用，技术上完全可以把这三件事串在同一个工作台里。但市面上的通用 AI 助手是为大众设计的，不懂科研的规矩：

  • 说错了数据不脸红——科研最怕「编造」；
  • 给出的文献可能是假的——科研最怕「查无此文」；
  • 写得越像越好、越省事越好——科研有一条学术规范的红线。

所以，我们要做一个懂科研流程、守学术规矩的 AI 助手：把「数据—文献—写作」三件事放在同一个台面上，一次对话办完。

1.2 产品定位

一句话定位：面向硕士、博士等科研人员的 AI 科研工作台——用「说人话」的方式，帮他们更快地处理数据、找到文献、写好论文；同时它又是一个「技能宿主」，能直接加载科研圈子已有的各种 AI 技能。

展开来说，它在用户身边扮演四个角色（第四个是 V1.1 新增的）：

角色一 · 数据小助手 你把数据文件丢进来，用大白话说「帮我看看这三组数据有没有明显差别」，它替你算好、画好、并用不绕弯的话讲清楚结果意味着什么。

角色二 · 文献管家 你告诉它研究方向，它帮你检索、筛选、跟踪最新进展；你把十几篇论文丢给它，它帮你整理出一份带出处的「研究现状小结」。

角色三 · 写作伙伴 你给思路和素材，它帮你搭框架、换表达、调格式、核引用；但它绝不替你编造内容，也不替你拍板结论。

角色四 · 技能宿主（V1.1 新增） 科研圈已经积累了大量现成的 AI 技能（比如「按国标排参考文献」「R 语言出版级绘图」）。本产品可以直接加载并使用这些技能，用户不需要等我们一个个开发，也能用上社区里最好的能力。

定位要点（四句话讲透）

  1. 它做的是「搬运、整理、初稿」这类体力活，把人的时间释放出来去做真正需要判断力的事。
  2. 它服务的是「一次完整的科研任务」，而不是某一个孤立的软件功能。
  3. 它把自己定义为「工作台」而非「代写工具」——所有产出都必须可核查、由人来确认。
  4. 它不与技能生态竞争，而是加载它们——自己只做技能做不到的事。

1.3 我们创造的核心价值

价值 通俗解释 用户能感受到的变化
省时间 把重复劳动交给 AI 整理数据、调格式从「好几天」压缩到「几小时」
少切换 一个地方办完三件事 不用在四五个软件之间来回倒腾文件
更靠谱 每个说法都有出处，每次处理都有记录 不再担心「AI 随手编一个数据或文献」
用得上现成的 能直接加载社区已有的科研技能 不用等我们开发，好用的能力马上能用
零门槛 说人话就能用 不需要学编程、不需要记命令和菜单
更安心 未发表内容属于私密信息 数据归属清晰，可随时删干净

1.4 产品边界：我们明确不做什么

把边界说在前面，避免期望错位。以下内容不在本期产品范围内：

  • ✕ 不提供整篇论文的「从零代写」。我们只做协助，不做枪手。
  • ✕ 不伪造、不篡改、不美化实验数据。
  • ✕ 不提供绕过期刊规则的盗版论文下载。
  • ✕ 不替用户下学术结论（例如「你这个发现能不能成立」），这类判断必须由人来做。
  • ✕ 不承诺 100% 准确。所有 AI 输出都需要用户过目、确认后才能使用。
  • ✕ 不预装第三方技能（V1.1 新增）。我们只提供「加载技能」的能力，装什么由用户自己决定——理由见第六章。

1.5 产品形态：为什么是「工作台 + 技能宿主」

这一节回答一个关键问题：既然科研圈已经有几十个现成的 AI 技能，我们为什么不干脆做一个技能包？或者反过来，为什么不全靠自己开发？

三种可选形态的对比

形态 做法 优势 致命问题
A. 全自研 三大模块的每个功能都自己写 完全可控，体验统一 慢。而且要和已有成熟项目正面竞争，容易被淹没
B. 纯技能包 只做 .md 技能文件，寄生在别人的客户端里 快、轻、能借别人的用户 做不到跨会话的项目空间、跨能力串联、数据不出本机、长任务恢复——这四件恰恰是我们的核心价值
C. 工作台 + 技能宿主（✅ 选定） 自己做工作台，能加载别人的技能 既快又完整：能力靠生态，价值靠自己 需要先搭好执行环境（这是必须花的成本）

我们选定 C 的三条理由

  1. 技能生态已经是既成事实，硬碰不如收编。 调研显示科研类技能已有数十个，其中不乏大公司和知名机构的作品。与其做「第 N 个文献检索技能」，不如做「最好的科研技能运行环境」。
  2. 技能做不到的四件事，正好是用户最痛的地方。 技能每次运行都是全新的上下文——它记不住你上周整理的数据，也没法把「文献里读到的结论」直接接到「正在写的那段话」上。而「课题空间」解决的正是这个问题。
  3. 工作量能下降一个量级。 详见第十二章「版本升级说明」。

一句话总结这个形态：

能力从生态借，价值由自己做。我们只做技能做不到的那五件事：课题空间、技能加载、技能编排、本机处理、任务恢复。

二、目标用户与画像

2.1 用户范围

层级 人群 说明
核心用户 在读硕士研究生、博士研究生 有明确课题与论文任务，时间压力最大，是产品的主要服务对象
延伸用户 博士后、青年教师、高校科研人员、企业研发人员 需求相近，且往往带着学生一起用，是重要的传播节点

  • 电脑操作水平属于中等，绝大多数不写代码，也不熟悉专业统计软件；
  • 英文文献是刚需，但母语是中文，英文写作是普遍短板；
  • 所在学校或院所通常已购买文献数据库权限，但不一定会用、懒得切换；

2.2 三类典型用户画像

画像一 · 小硕｜硕士二年级 · 工科 - 处境：刚进实验室，一边帮师兄师姐跑数据做图，一边准备自己的第一篇小论文。 - 日常：用 Excel 记数据，用 Origin / SPSS 画图，但每次都要重新上网搜「这个图怎么画」。 - 最痛：不知道该用哪种分析方法；图反复返工；中文写得好，翻成英文就变成「中式英语」。 - 他想要：数据丢进去，直接出一张能放进论文的图；写好的中文段落能变成像模像样的学术英语。

画像二 · 阿博｜博士三年级 · 材料 / 生物 - 处境：目标是发 SCI，正在同时推进文献综述和实验验证。 - 日常：每天在 Web of Science、Google Scholar、知网之间切换，EndNote 里躺着几百篇 PDF。 - 最痛：文献太多读不完；很难快速判断「这个方向到底有没有人做过」；投稿前格式和引用总出错。 - 他想要：一句话问出「这个方向最新的进展」，拿到一份带出处的现状小结；参考文献自动排好。 - （V1.1 新增） 他已经装了 Cursor，也收集过一些科研相关的技能文件，但不知道怎么把它们串起来用。

2.4 典型使用场景

场景一 · 周一下午，小硕拿到一批新数据 他把仪器导出的 Excel 拖进工作台，说：「帮我清理一下这份数据，然后看看不同温度下样品的强度有没有显著差异，画一张能投稿的柱状图。」十分钟后他拿到清理后的数据、一张图和一段可以直接用的结果描述。

场景二 · 周三上午，阿博要摸清一个新方向 他所在的课题组准备切入一个陌生方向。他问：「2023 年以来，柔性钙钛矿太阳能电池的效率上有哪些主要进展？有哪些还没解决的问题？」他拿到一份带出处的小结，再从中挑出 12 篇精读。

场景三 · 周五晚上，青椒要交英文初稿 学生的中文初稿写好了，但英文表达不通顺。他把稿子放进去，选「学术英语润色」，逐句确认修改建议，同时让系统按目标期刊模板统一了格式和参考文献。

场景四 · 投稿前一天，做最后体检 他把定稿放进去，运行「投稿前检查」：摘要字数是否超限、图表编号是否连续、引用与文末列表是否一一对应、有没有引用了已被撤稿的论文。系统给出一份待办清单，他逐项处理。

场景五 · 一次任务串起三个技能（V1.1 新增） 阿博要做一份「研究现状小结」。他不需要分别操作三个工具——工作台自动完成编排：

  1. 调用文献检索技能，找到 12 篇相关论文；
  2. 调用数据提取技能，把各篇的关键结论和实验条件抽出来做成对照表；
  3. 调用绘图技能，把「不同方法的效率随时间变化」画成一张趋势图；
  4. 中途他需要接孩子，关掉应用窗口（应用最小化到系统托盘，任务在后台继续跑）。晚上回来打开，任务从中断处继续，之前的结果都在。

这个场景是纯技能形态做不到的——技能之间不共享状态，也不能跨会话保存。

3.2 底座一：技能加载与编排（V1.1 新增）

这个底座解决什么问题

科研圈已经积累了大量现成的 AI 技能。这些技能本质上就是一个个文件夹，里面放着一个叫 SKILL.md 的说明书——用纯文本写成，用记事本就能打开、就能改。本产品的任务，就是提供一个「插座」，让这些技能插上就能用，并且能把多个技能串起来完成一件完整的事。

D1-1 技能加载器（P0｜自研）

  • 用户故事：作为一个已经在用 AI 工具的研究生，我手里已经攒了几个技能文件夹，我希望直接拿来用，而不是重新配置一遍。
  • 需求描述
  • 支持从本地文件夹或代码仓库地址加载技能；
  • 同时兼容社区两种约定目录（这样用户已有的技能夹不用搬家、不用改名）：
    • .claude/skills/
    • .agents/skills/
  • 加载时读取每个技能的名称与用途说明；若技能自带许可证信息，一并展示。
  • 验收要点：把一个符合社区标准的技能文件夹放进去，能被正确识别并显示名称与用途；放入不符合标准的文件夹时，给出清晰的错误提示，而不是静默失败。

D1-2 渐进式加载（P0｜自研）

  • 用户故事：作为装了二三十个技能的用户，我不希望系统每次对话都把所有技能全文读一遍——那样又慢又贵。
  • 需求描述
  • 平时只记住每个技能的名称和一句话用途；
  • 只有当任务确实匹配某个技能时，才去读它的完整说明；
  • 技能里附带的参考资料，只在真正需要时才加载。
  • 验收要点：装载 50 个技能时，日常对话的响应时间与装 5 个时没有明显差别。
  • 为什么重要：如果每次都全量加载，装 100 个技能光「目录」就要消耗约一万字上下文——又慢又贵，这是行业公认的坑。

D1-3 技能检索与推荐（P1｜自研）

  • 用户故事：作为装了太多技能的人，我希望系统告诉我「这件事该用哪个技能」。
  • 需求描述：根据当前任务，从已装技能中挑出最相关的 3–5 个候选，并说明推荐理由。
  • 验收要点：推荐理由必须具体（说清为什么这个技能合适），不能是「猜你喜欢」式的模糊表达。

D1-4 技能编排（P0｜自研）

  • 用户故事：作为要完成一件复杂任务的人，我希望系统自动把几个技能串起来，而不是我手动一步步操作。
  • 需求描述
  • 一次任务中可以按顺序使用多个技能；
  • 上一个技能产出的结果，能直接交给下一个技能使用（通过课题空间传递）；
  • 用户可以查看每一步用了哪个技能、产出了什么。
  • 验收要点：至少能跑通「检索 → 提取 → 绘图」这类三段式任务；中途任一步失败时，已完成的步骤结果保留，可从失败处重试。
  • 这是护城河：单个技能做不到串联，这是工作台存在的核心价值之一。

D1-5 技能管理与可见性（P1｜自研）

  • 用户故事：作为用户，我要清楚知道我这台机器上装了哪些技能、它们从哪来、什么许可证。
  • 需求描述：提供技能列表，展示名称、用途、来源、版本/提交记录、许可证；支持启用/停用、卸载。
  • 验收要点：每个技能都能追溯到具体的来源和版本。

D1-6 兼容性降级提示（P1｜自研）

  • 用户故事：作为用户，我不想以为某个功能能用、结果它静默失灵了。
  • 需求描述：部分技能依赖特定客户端的专有能力，在本产品中可能失效。系统应在加载时检测并明确提示「此技能的某些功能在当前环境不可用」，并说明哪些部分仍可用。
  • 验收要点：宁可提示不可用，也不假装能用然后静默失败。
  • V1.6 排期说明（补上一条依赖时序）：本项整体排在阶段二，但其中「加载时检测」这一部分必须提前到阶段一。 原因很简单——阶段一第一个月就要「借用技能」，而社区技能依赖特定客户端专有能力（如某些专有工具字段）的情况从第一天就会出现。 若不提前，兼容问题会以"静默失效"的方式消耗试用用户的信任——这与本项「宁可提示不可用」的原则直接冲突。 因此 12.2 表中本项的计划阶段标注为「二（"加载时检测"提前至一）」。

3.3 底座二：执行环境（V1.1 新增）

这个底座解决什么问题

SKILL.md 里除了文字说明，往往还附带可执行的脚本（比如「按这个脚本清洗数据」「用这段代码画图」）。一个只会聊天的网页跑不了这些脚本——那样技能就退化成「一段提示词」，白瞎了。

所以必须先给工作台配好「手脚」：能读文件、能跑代码、能上网、能连外部数据源。

这是 V1.1 最重要的技术判断：不搭执行环境，第六章说的「加载技能」就只是纸面能力。

V1.2 架构修正：执行环境必须分两层

V1.1 把执行环境当成一件事，沙箱选型评估后（详见 12.4）修正为必须分两层——因为用户自己的电脑（Windows / macOS）和服务器，能用的技术完全不同：

层 运行在哪 技术方案 承担什么 计划阶段
云端沙箱层 自托管服务器 / 云 CubeSandbox（首选） + E2B 兼容接口 技能脚本执行、重计算任务 阶段一
本机执行层 用户自己的电脑 microsandbox（首选，跨三平台）；轻量场景可用系统级隔离（V1.3 已明确，见 12.4） 「敏感数据本机处理」+ 本机执行技能脚本 阶段一后半段 🟡 建议，待确认（见 12.3 A4）

V1.6 口径统一：本机执行层的排期此前在 3.3 D2-2、3.3 上表、12.2 的 C-4、12.3 A4、12.5 决策表、阶段二正文共六处出现过六种说法（"推迟阶段二"/"阶段一后半段"/"视进度决定"/"待资源盘点"…）。V1.6 起统一为一句：🟡 建议放在阶段一后半段，待 12.3 A4复盘确认；若不满足则顺延至阶段二，并在产品内明示"本机模式的能力边界"。

V1.3 更正：V1.2 曾判断「本机执行层必须推迟到阶段二」，理由是"桌面端跑不了沙箱"。这个判断是错的——起因是当时只评估了 CubeSandbox 一个项目，而它依赖 KVM，就顺势推断成了"桌面端不行"。补充核实后确认：本机沙箱在 Linux / macOS / Windows 三个平台上都有成熟方案（详见 12.4）。

这带来一个关键的好消息：PRD 5.6 承诺的「敏感数据本机处理」与「能执行技能脚本」可以同时成立——不再需要让用户在"数据安全"和"能力完整"之间二选一。

V1.5 补充：技术栈已定案（Tauri 外壳 + Python 内核），并要牢记"两套 Python"

宿主内核的 Python 沙箱内的 Python
职责 技能加载、文件访问、任务调度、调用沙箱 真正执行技能脚本与 AI 生成的代码
信任级别 可信（我们自己写的） 不可信（可能来自社区技能）

D2-1 文件访问（P0｜自研）

  • 需求描述：在工作台内读写用户授权的本地文件（数据表、PDF、稿件等）；所有访问都在用户可见、可撤销的授权范围内。
  • 验收要点：未授权目录不可访问；授权记录可查、可随时收回。

D2-2 代码沙箱（P0｜自研 + 借力）

  • 需求描述：AI 生成的分析代码、技能附带的脚本，在隔离的沙箱环境中运行，与用户本机系统隔离；运行结果（数字、图表、日志）回传到工作台。
  • 技术选型（V1.2 确定）
  • 首选：CubeSandbox（TencentCloud/CubeSandbox，腾讯云开源）。理由：许可证干净（Apache-2.0）、兼容 E2B SDK 因而不会被锁定、MicroVM 硬件级隔离、平均 <60ms 冷启动且单沙箱开销 <5MB。完整评估见 12.4。
  • 接口层按 E2B 标准写：这样后端可以随时在 CubeSandbox、E2B 云或其它实现之间切换，零业务代码改动。这是本选型最重要的战略价值。
  • 本机（Windows / macOS）不走这条路线——CubeSandbox 依赖 KVM，桌面端无法运行。本机执行层改用桌面端方案（microsandbox 首选，见 12.4 第五节），排期同 3.3 底座二开头表格：🟡 建议放在阶段一后半段，待 12.3 A4确认。
  • 验收要点
  • 沙箱内的代码无法访问沙箱外的文件；
  • 沙箱运行失败时给出可读的错误说明，而不是一堆报错栈；
  • 密钥等敏感凭证不进入沙箱（CubeSandbox 的凭证托管能力可满足，见 5.7）。
  • V1.6 补充：必须定义「统一执行接口」（评估报告指出的架构缺口） 目前「接口层按 E2B 标准写」只覆盖了云端；本机的 microsandbox 用的是它自己的 SDK。而 D1-4 技能编排要同时面对两种后端——同一个「跑一段脚本」的请求，落在本机还是云端、结果如何回传、检查点存在哪，如果两层各自实现，编排层的工程量会因此膨胀，也会长期背上"两套排障路径"的维护负担。 因此要求：定义一套统一执行接口（起沙箱 / 执行 / 取结果 / 打快照 / 网络策略），编排层只认接口、不认后端；接口层用同一套用例同时跑通两种后端（对应 12.6 检查清单第 8 项）。

D2-3 网络访问与白名单（P0｜自研）

  • 需求描述：允许技能访问必要的学术数据来源（论文库、文献元数据接口等）；非白名单地址不予放行。
  • 验收要点：访问被拦截时给出原因说明；用户可在设置中查看和调整白名单。

D2-4 外部数据源接入（P1｜借力）

  • 需求描述：支持通过业界通用的「外部工具接入标准」连接数据库、文献管理系统等（即 MCP 协议）。用户已有的数据源可以挂进来。
  • 验收要点：接入的外部数据源在界面上可见、可断开。

D2-5 权限提示与显式授权（P0｜自研）

  • 用户故事：作为用户，我不能接受「技能悄悄干了什么我都不知道」。
  • 需求描述：任何涉及执行代码、读写文件、联网、调用外部数据源的操作，都必须先向用户提示，得到确认后才执行；提供「本次允许 / 始终允许」的选择。
  • 验收要点：不存在任何静默执行的路径；权限记录可查。

D2-6 模型接入与密钥管理（P0｜自研）—— V1.6 新增

  • 用户故事：作为用户，我要能自己决定用哪个模型、自己管住密钥，并且清楚知道每次任务花了多少。
  • 需求描述
  • 支持用户配置模型服务（BYOK，用户自带密钥）：填入密钥、选择模型、测试连通性；
  • 支持配置多个来源，并按任务难度指定使用哪一个（对应 5.3「按难度用不同的能力」）；
  • 密钥加密保存在本机，不进入沙箱，不上传、不同步；
  • 记录每次任务的模型调用量与估算费用，支持设置月度提醒。
  • 验收要点：密钥不以明文落盘；更换密钥后新任务立即生效；费用数据可查、口径说明清晰。
  • 为什么必须自研：这是产品自己的发动机，也是 5.3 成本控制与 C-5 资源消耗透明的地基。完整策略（BYOK / 代理的取舍、首发供应商、密钥安全、计量口径、本地模型）见 5.11。

3.4 模块一：数据处理与分析辅助

模块目标 让不会统计、不会编程的科研人员，也能独立把原始数据变成「可用的结论 + 可发表的图表」。

M1-1 自然语言数据处理（P0｜借力 + 自研）

  • 用户故事：作为一个不会选统计方法的硕士生，我想把数据文件直接拖进来、用一句中文说清我要什么，就能拿到结果，而不是先去学一遍统计教材。
  • 需求描述
  • 支持上传常见表格文件（Excel、CSV、TXT 等）与图片中的数据表；
  • 用户可用中文或英文口语化描述诉求；
  • 系统理解意图后，自动完成数据整理与分析，并给出结果；
  • 结果必须配一段非统计专业语言的解释。
  • 实现方式：分析执行依托成熟的统计计算能力（借力）；「听懂大白话」和「讲清结果」由我们自研。
  • 验收要点：能正确读出常见表格文件；对「求平均 / 两组对比 / 看相关性 / 看趋势」等常见诉求能给出合理结果；解释部分不出现未加说明的统计术语。
  • 边界：不替用户设计实验方案；不替用户判断学术结论是否成立。

M1-2 数据清洗与整理（P0｜借力 + 自研）

  • 用户故事：作为被数据折磨的博士生，我想让系统先帮我把脏数据找出来，再决定怎么处理。
  • 需求描述
  • 自动识别：缺失值、重复行、明显异常值、格式不统一（日期格式、单位、大小写）；
  • 以清单形式提示问题 + 建议处理方式，由用户勾选确认后执行；
  • 保留处理前后的对照，支持一键撤销。
  • 验收要点：问题清单必须给出「在哪一列、有多少条」；处理动作必须可撤销；默认不自动修改数据，需用户确认。

M1-3 统计分析与检验（P1｜借力 + 自研）

  • 用户故事：作为要写结果章节的研究生，我想知道该用哪种方法，并被告知有没有什么前提条件没满足。
  • 需求描述：覆盖描述统计、组间比较、相关性分析、回归分析、方差分析等常见场景；自动判断适用条件并主动提醒（如「样本量偏小，结论需谨慎」）。
  • 验收要点：能给出所选方法的名称与「为什么选它」的大白话说明；前提不满足时必须提示，不可静默出结果。
  • 边界：不承诺统计结果等同于学术结论；复杂建模场景本期不覆盖。

M1-4 图表生成（P0｜借力）

  • 用户故事：作为要投稿的研究生，我想要一张不用返工的、符合期刊要求的图。
  • 需求描述
  • 一句话生成常用图表：折线图、柱状图、散点图、箱线图、热力图等；
  • 可按目标期刊要求调整字体、配色、尺寸、清晰度、坐标轴样式；
  • 支持导出高清图片与可再次编辑的源文件；
  • 支持「在原有图上改」——用户指出不满意的点，系统局部调整。
  • 实现方式：优先借用社区现成的科研绘图技能（已有 R / ggplot2 等成熟技能），我们只负责「听懂需求」和「把结果接进课题空间」。
  • 验收要点：常见图表一次生成即可用；导出图片满足投稿清晰度要求；图与数据源保持联动。
  • 边界：不保证符合某本具体期刊的全部细节要求，最终仍需用户核对投稿指南。

M1-5 结果解读与写作素材（P1｜自研）

  • 用户故事：作为不太会写「结果」章节的研究生，我想要一段能直接拿来改的草稿。
  • 需求描述：把分析结果转写成可直接放入论文「结果」部分的中文或英文段落草稿；段落中每一个关键数字都标注来源，并明确提示「以下数字请务必核对」。
  • 验收要点：草稿中的数字必须与分析结果完全一致，不得出现任何未经计算的新数字。
  • 为什么自研：现有技能都在做「生成图表」，几乎没人做「用大白话解释结果」——这正是差异化所在。

M1-6 图片与图表理解（P1｜自研）

  • 用户故事：作为在读文献的博士生，我想让系统先帮我看懂一张图在表达什么。
  • 需求描述：上传实验图片或已有图表，系统描述内容、提取趋势、指出可能存在的问题（如缺少误差棒、坐标轴单位缺失）。
  • 验收要点：描述须基于图片可见信息，不得推测图中不存在的结论。

3.5 模块二：学术文献检索与推荐

模块目标 把「找文献、读文献、管文献」从体力活变成一次对话，并保证每一条文献都真实可查。

M2-1 自然语言检索（P0｜借力）

  • 用户故事：作为阿博，我想直接问一句完整的话，就得到相关文献清单，而不用自己拼关键词组合。
  • 需求描述
  • 支持中英文自然语言提问；
  • 结果包含：标题、作者、期刊、年份、摘要要点、原文链接或编号（DOI）；
  • 支持按年份、类型、影响力等条件筛选与排序；
  • 结果必须来自真实、可核查的学术来源；若相关信息不足，须明确说明「暂未找到」，不得凭空生成。
  • 实现方式：优先借用现成技能或成熟检索实现，不自研检索算法。
  • 验收要点：随机抽查结果，链接可打开、文献确实存在；对查不到的问题必须承认查不到。
  • 边界：仅提供公开可获取的来源与合规接口，不提供盗版下载。

M2-2 综述与对比整理（P0｜借力 + 自研）

  • 用户故事：作为要写文献综述的博士生，我想把选中的十几篇文献交给系统，先得到一份结构化的现状小结。
  • 需求描述
  • 用户勾选若干篇文献，一键生成「研究现状小结」；
  • 小结须包含：主要方法、核心结论、彼此分歧、尚未解决的问题；
  • 每一个观点后面必须标注它来自第几篇文献，可点击跳转核对。
  • 验收要点：小结中不得出现未标出处的观点；不得把某篇文献的结论张冠李戴到另一篇上。

M2-3 方向追踪与个性化推荐（P1｜借力）

  • 用户故事：作为怕错过新进展的博士，我想设定关注方向后，定期收到相关的、有理由的推荐。
  • 需求描述：用户设定关注方向、关键词或学者；系统定期推送新文献；每条推送说明推荐理由，并支持一键取消关注。
  • 验收要点：推送可设频率与关闭；推荐理由必须具体。

M2-4 文献管理与阅读辅助（P1｜借力）

  • 用户故事：作为收藏了几百篇 PDF 的博士生，我想让这些论文变得「可以对话」。
  • 需求描述
  • 文献收藏夹与标签管理；
  • 上传 PDF 后可：提问、生成摘要、提取图表与数据、翻译指定段落；
  • 支持导出为主流文献管理软件可识别的格式（避免用户被锁定）。
  • 验收要点：回答必须基于该 PDF 内容，并标注页码或段落位置。

M2-5 引用与参考文献格式（P0｜借力）

  • 用户故事：作为被参考文献格式折磨的人，我想让系统自动排好，并且正文和文末一一对应。
  • 需求描述：自动生成参考文献条目，支持主流格式（APA、MLA、GB/T 7714 及常见期刊模板）；与写作模块打通，正文引用插入后，文末列表自动同步。
  • 实现方式：借用已有的引用格式标准库与现成技能（引用格式引擎已有成熟现成方案，不要自研）。
  • 验收要点：引用编号连续、正文与列表一一对应；格式切换时全篇一次性更新。

M2-6 相似表述提示（P2｜借力）

  • 用户故事：作为投稿前紧张的研究生，我想在被指出问题之前，先得到提醒。
  • 需求描述：对稿件中可能与已有工作高度相似的表述给出提示，并建议「此处可能需要标注引用」。
  • 验收要点：只做提示，不下「是否抄袭」的判定。
  • 边界：不替代正式查重工具。

M2-7 引用真实性核验（含撤稿检查）（P0｜自研）—— V1.1 新增

  • 用户故事：作为要投稿的作者，我最怕的是「引了一篇根本不存在的文献」，或者更糟——引了一篇已经被撤稿的论文自己还不知道。
  • 需求描述
  • 对稿件中的每一条引用，逐一核验：是否真实存在、能否打开、作者年份卷期是否对得上；
  • 检查该文献是否已被撤稿，若已撤稿则给出显著警示；
  • 对无法核实的引用，明确标注「未能核实，请人工确认」，绝不默默放过；
  • 生成一份「引用核验报告」，逐条列出核验结果。
  • 为什么必须做，而且要自研
  • 行业实测：主流大模型生成的引用中，78%–90% 是编造的；一项覆盖 250 万篇论文、1.11 亿条引用的审计研究保守估计，仅 2025 年一年就产生了约 14.7 万条虚构引用。
  • 「自信地引用一篇被撤稿的论文，比什么都不引用更糟」——这是学术场景的硬底线。
  • 现有技能几乎没人做这一块，这是我们最能体现产品定位的地方。
  • 数据源方案（V1.6 新增，已核实）——此前这一条是空的，而它是本功能能否落地的前提：

  • 验收要点：核验结果必须逐条可查；无法核实时必须显式标注；撤稿警示不可被忽略。
  • 落地前提：数据源的访问条款、频控约定与商用范围需在接入前逐家读一遍并留档（对应 10.3）；阶段零第 1 周完成可得性核查（见里程碑表）。
  • 这是第一阶段的旗舰功能，优先级高于任何「锦上添花」的能力。

3.6 模块三：论文写作辅助

模块目标 帮用户把「想法 / 数据 / 文献」变成「结构清晰、语言规范、格式正确的论文稿」，但不代写、不编造。

M3-1 选题与大纲（P1｜自研）

  • 用户故事：作为刚开题的研究生，我想要一份可讨论的论文结构建议。
  • 需求描述：输入研究方向与已有材料，输出论文结构建议（各章节要写什么、大致篇幅），并说明这样安排的理由。
  • 验收要点：结构建议须结合用户提供的研究内容，不输出与课题无关的通用模板。

M3-2 段落写作协助（P0｜自研）

  • 用户故事：作为中文思维、英文表达的研究生，我想有人帮我把话说明白。
  • 需求描述：提供三种模式—— 1. 中译学术英：用户写中文，系统输出学术英文表达； 2. 英文润色：用户写英文，系统改善语法与地道度； 3. 要点扩写：用户给要点，系统扩写成段落（必须明确标注这是草稿，事实需用户确认）。 支持选择语气与风格（如「更严谨」「更简洁」「更贴近该期刊风格」）。
  • 验收要点：改写不得改变原意、不得增删事实；扩写内容须带「待核实」标记。

M3-3 语言润色与翻译（P0｜自研 + 借力）

  • 用户故事：作为要交稿的作者，我想逐句确认系统改了什么，而不是被整体覆盖。
  • 需求描述：语法纠错、学术表达替换、中式英语改写、中英互译；逐句对照展示，用户可逐条接受或忽略；提供「为什么这样改」的简短说明。
  • 实现方式：通用润色可借力现成技能；「中式英语改写」是我们重点自研的差异点——中文母语科研人员的真实痛点，现有工具做得都不够细。
  • 验收要点：原文与建议稿并列可见；接受/忽略状态可随时更改；未接受的建议不得写入正文。

M3-4 结构与逻辑检查（P1｜自研）

  • 用户故事：作为想提前发现问题的作者，我想要一个「审稿人视角」的意见列表。
  • 需求描述：检查逻辑跳跃、论证不充分、章节衔接生硬、结论与数据不匹配等问题；以批注形式呈现，不改动正文。
  • 验收要点：每条批注须指明位置与具体问题；批注可逐条标记「已处理 / 忽略」。

M3-5 格式与投稿准备（P0｜自研 + 借力）

  • 用户故事：作为投稿前夜焦虑的作者，我想要一份照着做就行的检查清单。
  • 需求描述
  • 按目标期刊模板统一字体、行距、标题层级、图表编号与参考文献格式；
  • 生成投稿前检查清单（摘要字数、图表数量与编号、伦理声明、作者信息等），逐项可勾选。
  • 实现方式：排版引擎与国标格式借用现成技能；中文期刊模板库与检查清单自研。
  • 验收要点：格式调整全篇一致；清单项须可定位到正文具体位置。

M3-6 版本与协作（P2｜自研）

四、典型使用流程

建立课题空间→ 用一句话提需求→ 系统确认关键动作→ 拿到结果与出处→ 按需微调→ 导出落地
下面是四个具体场景，都按「用户说什么 → 系统做什么 → 用户得到什么」来写。

以下流程都写「用户说什么 → 系统做什么 → 用户得到什么」，用于帮助非技术伙伴建立直观印象。

场景 A：从实验数据到一张论文插图

前置：小硕手上有一份仪器导出的 Excel。

  1. 建立课题空间：新建「XX 材料热稳定性实验」课题，把数据文件拖进来。
  2. 说需求：在对话框输入「这份数据有点乱，帮我清理一下，然后比较 25℃、50℃、75℃ 三组的强度，画柱状图」。
  3. 系统反馈问题清单：「检测到第 3 列有 5 处缺失值、第 7–9 行重复、单位不统一（部分为 MPa、部分为 Pa），建议……」。用户勾选确认。
  4. 系统执行：完成清理，给出三组对比结果，附一段大白话解释与「以下数字请核对」的提示。
  5. 出图微调：生成柱状图。用户说「配色换成灰阶，字号大一点」，系统局部调整。
  6. 落袋：导出高清图片与源文件；同时得到一段可直接放进「结果」章节的草稿。

结果：原本需要半天到一天的工作，压缩到十几分钟；数据与图保持联动，后续改数据可一键重绘。

场景 B：三天内摸清一个新方向

  1. 提问：阿博输入「2023 年以来，柔性钙钛矿太阳能电池的效率上有哪些主要进展？还有哪些没解决的问题？」
  2. 浏览清单：系统返回按相关度排序的文献列表（含标题、期刊、年份、摘要要点、DOI 链接）。
  3. 筛选：他勾选 15 篇加入课题空间，其余忽略。
  4. 生成现状小结：一键得到按「主要方法 / 核心结论 / 分歧点 / 未解决问题」组织的小结，每个观点后带文献编号。
  5. 逐条核对：点击编号可跳转原文核对，发现两条与自己理解不符，手动调整。
  6. 设定追踪：把该方向设为关注，之后定期收到新文献推送。

结果：从「盲目下载五十篇」变成「精准精读十几篇」。

场景 C：把中文初稿变成可投稿的英文稿

  1. 上传初稿：青椒把学生写的中文初稿放入课题空间，同时上传目标期刊的投稿指南。
  2. 语言转换：选择「中译学术英」，系统逐句给出英文建议，并说明修改理由。
  3. 逐句确认：他逐条接受或忽略，遇到专业表述直接手动改写。
  4. 结构与逻辑体检：运行「审稿人视角」检查，得到批注清单。
  5. 格式统一：套用期刊模板，统一字体、行距、图表编号；参考文献自动生成并与正文同步。
  6. 投稿前检查：生成清单，逐项确认摘要字数、图表数量、伦理声明等。

结果：第一轮粗活交给系统，人只做真正需要判断力的部分。

场景 D：投稿前的最后一遍体检

  1. 上传定稿
  2. 运行「投稿前检查」→ 得到待办清单（摘要超字数 23 词、图 3 与图 4 编号重复、参考文献第 12 条与正文不对应）
  3. 运行「引用真实性核验」→ 发现第 27 条引用所指向的论文已被撤稿，系统给出显著警示
  4. 逐项处理后重新检查
  5. 通过，安心投稿

第 3 步是 V1.1 新增的。这个功能救回的可能是一篇论文，也可能是一个人的学术生涯。

场景 E：一次任务串起三个技能（V1.1 新增）

  1. 阿博在课题空间里说：「帮我把这个方向的现状整理一下，做成一份带趋势图的小结。」
  2. 工作台自动编排： - 文献检索技能 → 找到 12 篇相关论文，存入课题空间； - 数据提取技能 → 抽取各篇的研究方法、实验条件与结论，做成对照表； - 绘图技能 → 画出「不同方法效率随时间变化」的趋势图。
  3. 中途他关掉应用窗口去接孩子（应用最小化到托盘常驻，任务在后台继续）。
  4. 晚上回来打开，任务从中断处继续，之前的结果都在，且能看到每一步用了哪个技能。
  5. 他逐条核对结论，修改两处，导出成 Word。

这个场景是纯技能形态做不到的——技能之间不共享状态，也不能跨会话保存。这正是「工作台」的价值所在。

5.4 准确性与可靠性

  • 可溯源：所有涉及事实、数字、文献的输出，都必须能点开看到来源；
  • 不编造：无法确定时必须明确说「不确定 / 未找到」，禁止用看似合理的假信息填补；

  • 二次确认：涉及关键结论、数据修改、引用插入的操作，必须由用户确认后才生效；
  • 可纠错：用户可一键举报错误回答，并说明错在哪；
  • 有交代：明确的「AI 可能出错」提示常驻可见。

5.5 长任务可靠性（V1.1 新增）

这是我们自己在调研中发现的行业空白：几乎所有同类工具都做不到。

要求 具体标准
可中断 长任务随时可暂停，用户可关掉窗口去做别的事（桌面形态下的具体机制见下方「V1.6 补充」）
可恢复 回来后从中断处继续，不需要从头再来

V1.6 补充：桌面形态下的任务生命周期（此前缺失，是一条 P0 承诺的架构缺口）

V1.5 定案桌面应用后，本节的表述需要重新设计。原因很直接：

⚠️ 网页时代，"关掉浏览器"意味着"关掉客户端"，服务器上的任务照跑；桌面应用不一样——关掉窗口的默认行为是退出进程，并连带终止执行内核（Python sidecar）。也就是说，这条 P0 承诺在桌面形态下反而更难兑现，不能靠"默认行为"侥幸。

V1.6 明确按以下机制设计：

环节 设计 说明
后台续跑 关闭主窗口时，应用最小化到系统托盘常驻，任务继续在后台执行 默认行为；托盘图标显示任务进度与状态
退出保护 用户若选择「完全退出」，退出前自动打一次任务检查点（已完成步骤与中间产物写入课题空间） 避免"不小心退出、全白干"
恢复入口 下次启动时，若检测到未完成任务，在首页显著位置提供「继续上次任务」 不做静默续跑，是否继续由用户决定
本机沙箱状态 本机 microsandbox 的快照能力用于保存沙箱内运行状态（见 12.4 第五节） 与云端沙箱快照能力对齐

这是阶段一开工前必须落地的设计，不是可以后补的细节——它决定「长任务可恢复」这条 P0 承诺到底成不成立。检查清单里对应 12.6 的落地项，设计定案后需回填本章。

5.6 数据安全与隐私（科研场景尤为关键）

  • 未发表的实验数据与论文属于高度敏感信息，默认私密保存，不用于对外展示，不进入公开训练；
  • 提供「敏感数据本机处理」选项（V1.1 由 P2 提至 P1）——该模式下文件与数据不离开用户电脑；
  • 不同课题空间之间严格隔离（V1.6 订正：本产品首期为桌面本地应用，不预设云端账号体系。此前"删除账号""不同用户之间隔离"是多租户云服务的语言，与形态不符——未来若引入云同步或机构版，届时再单独定义账号与多租户隔离规则，见阶段三）；
  • 用户可随时导出全部数据、一键彻底清除本机保存的全部内容；
  • 隐私条款提供「大白话版」，一页看懂我们收集什么、不收集什么。

V1.6 新增：数据流向与承诺边界（不讲清楚，「数据不出本机」这句话经不起推敲）

先承认一件事：「数据不出本机」如果被理解成"任何数据都不出电脑"，那是不准确的。 只要调用大模型，提示词就必然要发往模型服务。所以正确的做法不是喊一句做不到的口号，而是按模式把边界画出来：

模式 文件与数据 发往模型的内容 发往云端沙箱的内容 对外承诺措辞
默认模式 保存在用户电脑 完成当前任务所必需的内容片段（按 5.3「先筛后做」控制范围） 需要执行脚本时，上传对应数据 「文件保存在本机，按需处理」
敏感数据本机处理模式 不离开本机 仍会发送模型调用所必需的内容；若配置了本地模型（见 5.11），则可做到全链路零出网 无（脚本在本机沙箱执行，见 12.4） 「文件与数据不出本机；模型调用内容见流向说明」

对外统一口径（重要）：不宣称"完全不出网"，只承诺"文件与数据不出本机"，并主动说明模型调用会发送什么。 把边界说清楚，比喊一个做不到的口号更能建立信任——这是科研用户最在意的一点。

待补：本节目前是文字描述，阶段一开工前需补一张直观的数据流向图（评估报告 3.5 缺口 1、建议 5.2 第 10 条）。

5.7 技能安全（V1.1 新增）

引入第三方技能带来新的风险面，必须有对应约束：

要求 具体标准
不预装 产品不内置任何第三方技能；装什么完全由用户决定
安装前透明 安装前展示技能来源、许可证、将要用到的权限
授权后执行 涉及执行代码、读写文件、联网的操作，必须显式授权

出站流量可控（V1.2 新增） 沙箱内的代码只能访问白名单地址；CubeSandbox 提供基于 eBPF 的出站过滤，与 D2-3 的能力要求一致

5.10 可维护与可扩展

  • 模块独立：三大模块与两个底座可各自升级；
  • 可接入：后续可接入新的学术数据来源、新的期刊模板、新的技能格式；
  • 可观测：系统能记录「哪一步最常失败」，作为持续改进的依据；
  • 可延续：数据格式与导出方式保持通用，避免用户被锁定。

5.11 模型供给与密钥管理（V1.6 新增）

为什么必须单列一节：整个产品靠大模型驱动，但此前 PRD 全文没有一处回答"模型从哪来"。 这一节补上之后，5.3 成本控制、C-5 资源消耗透明、5.6 的"敏感模式"才有落地的地基。 本节内容对应功能项 D2-6。

一、供给策略：桌面优先 BYOK，首期不做代理

方案 是什么 选择 理由
BYOK（用户自带密钥） 用户在设置里填入自己的模型服务密钥，产品直接调用 ✅ 首期采用 ① 桌面应用天然适合——密钥只存在用户本机，我们不承担密钥托管责任；② 成本与责任清晰，用户按自己用量付费；③ 我们不向公众提供生成式 AI 服务，合规负担最低（见第十章的合规说明）
产品代理（我们转发请求） 用户使用我们提供的账号与额度 ⏸ 首期不做，机构版再评估 一旦做代理，我们即成为服务提供方，需承担相应的合规义务与成本垫付；且与"数据不出本机"的定位相互拉扯

二、首发支持的模型来源

类别 说明
国产模型 优先支持——国内可直连、合规清晰。具体首发清单需在阶段零调研后确定，已列入 12.3 待确认项
海外模型 支持用户自行填入（BYOK 模式下，网络条件由用户自行解决）
本地模型（重点） 支持接入在本机运行的模型服务。只有这一条能实现「敏感数据本机处理」模式下的全链路零出网（见 5.6）——这是本地模型对我们的特殊价值，不只是"省钱"
多模型并存 用户可配置多个来源，并按任务难度分级调用（对应 5.3「按难度用不同的能力」）：轻任务用便宜模型，难任务才动用强模型

三、密钥安全（与 5.7 呼应）

  • 密钥只保存在用户本机，加密存储——使用操作系统提供的密钥链 / 凭据管理器，不落地成明文文件；
  • 密钥不进入沙箱（对应 5.7「凭证不进沙箱」）——技能脚本永远拿不到用户的密钥，由内核代持并代理调用；
  • 不上传、不同步、不做任何形式的集中收集；
  • 用户可随时在设置中查看、替换、删除。

四、资源消耗的计量口径（C-5 的地基）

计量项 口径

按课题空间汇总 用户可查看某个课题的累计消耗
预算提醒 支持设置月度上限，接近上限时提醒（不强制中断任务，是否继续由用户决定）
展示位置 每次任务完成后在结果旁显示；汇总数据在课题空间内可查

验收要点：用户在不看文档的情况下，能回答"我上周花了多少钱、花在哪几个任务上"。

五、风险与前提

  • BYOK 模式下，模型质量与网络条件由用户自行承担——产品需在引导中说明"结果质量与所选模型有关"；
  • 供应商清单与定价随市场变化，需按季度复核；
  • 5.3 的成本控制三条原则依赖本节的计量口径，两者必须同时落地。

六、技能生态策略（V1.1 新增）

这一章是 V1.1 新增的核心章节，解释「宿主」身份具体怎么落地。

6.1 一句话原则

能力从生态借，价值由自己做。不预装、不锁定、不静默。

6.2 我们加载什么样的技能

类别 做法
通用科研技能 直接加载，用户自行选择
中文科研场景技能 优先推荐（国标排版、中文期刊模板、中文科研绘图等）
我们自己开发的技能 作为「可选推荐」，同样不预装，用户可自由卸载
需要授权的数据源连接 用户自行配置

6.3 不预装原则（重要）

产品默认不带任何第三方技能。

原因有三：

  1. 责任边界清晰。技能是别人写的，装不装、装哪个由用户自己决定。这就像浏览器不预装扩展，但提供加载扩展的能力。
  2. 许可证风险可控。技能仓库的许可证和每个技能文件的许可证可能不一致，预装就等于我们在替用户承担再分发的合规风险。
  3. 避免背上维护责任。预装的技能一旦出问题，用户会认为是我们的问题。

如果未来要做「官方推荐技能清单」，必须建立严格的白名单流程，逐个技能核对许可证与代码安全性。

6.4 许可证红线

以下类型的技能绝对不能进入预装或官方推荐名单：

类型 通俗说明
禁止商用类许可 这类许可写明「不得用于商业用途」，一旦我们把它打包分发，可能直接违反授权
强传染性开源协议 这类协议要求「你用了我的代码，你的项目也必须同样开源」，会迫使我们放弃商业空间

结论：只收录宽松许可的技能；对不明确的，一律不收录。

6.5 上游依赖的风险与应对

风险 说明 应对
技能质量参差 随便装一个技能可能出错，甚至包含有害脚本 安装前审查 + 沙箱隔离 + 权限提示
技能「断供」 作者删库、改名或变更许可 锁定版本，不自动跟随最新版
兼容性缺口 部分技能依赖特定客户端的专有能力 加载时检测并明确提示哪些功能不可用
上下文爆炸 技能太多会拖慢并增加成本 渐进式加载 + 技能检索推荐

6.6 与技能生态的关系定位

我们不做 我们做
再写一个「文献检索技能」 提供最好的科研技能运行环境
和头部技能项目正面竞争 让用户一次配好、全部能用
把技能绑死在我们的产品里 用户的技能文件可以随时带走

二、按团队情况选择排期方案（三选一）

评估报告给出了三套可选做法，按团队条件选择：

方案 做法 适合 代价
A · 保决策、放宽排期 阶段一延长至 4.5–5 个月，其余决策不动 团队 ≥ 4 人、有服务器与运维资源 整体上线推迟 1–2 个月
B · 本机优先（本 PRD 倾向） 阶段一只做本机沙箱（microsandbox + 降级路径），云端沙箱层推到阶段二 团队 3–4 人、没有服务器资源 省掉服务器与运维两座山；MVP 期 30–50 人规模下重计算需求有限，「数据不出本机」反而成为首发主打卖点；代价是硬件不满足者走降级路径，需在产品内明示能力边界
C · 垂直场景聚焦 阶段一砍掉模块一（数据），聚焦「文献 + 写作 + 引用核验」一条线（场景 B/C/D），数据模块整体后移 团队 ≤ 3 人 范围最小、最快验证；「三件事打通」的完整故事推迟到阶段二，阶段一成功标准需同步改写

十、开源与合规（V1.1 新增）

本项目计划开源，这一章把必须提前决定的事写清楚。

10.1 许可证选择

建议采用宽松型开源许可（推荐 Apache 2.0 或 MIT，前者多一条明确的专利授权条款，对企业和高校更友好，也是本领域最主流的选择）。

绝对不能引入的代码：

类型 处理方式
禁止商用类许可 只可参考思路，代码不得进入本项目
强传染性开源协议 谨慎——一旦引入，可能要求整个项目同样开源

建议做法：项目内建立一份「第三方来源与许可证清单」，任何借鉴的代码都登记在案。

10.2 学术署名提醒

如果把本系统写成论文发表，请先确认学校、导师和课题组对「开源时间点」与「论文投稿顺序」的要求。部分高校和期刊对「先开源后投稿」有明确规定。这一条建议在写第一行代码之前就问清楚。

10.3 文献数据来源的使用条款

即使接口是免费开放的，各家的调用频率、商用范围、是否要求署名规定不同。在把某个数据源写进产品之前，把它的使用条款读一遍——这是很多项目上线后才被发现的问题。

12.1 版本升级说明 —— 我们改了什么、为什么改

V1.0 → V1.1（产品形态的根本调整）

# 改了什么 V1.0 怎么写的 V1.1 为什么改
1 产品形态 隐含假设「三大模块全部自研」 生态调研发现科研类技能已有数十个成熟项目，其中不乏大厂与知名机构作品。全自研既慢又会被淹没 → 改为「工作台 + 技能宿主」
2 新增两个底座 无 有了「宿主」定位，就需要技能加载与编排、执行环境这两件事落地，否则加载技能只是纸面能力
3 阶段一范围 11 项 P0 全部自研 重排为「自研 5 件 + 借用技能 N 件」，工作量下降一个量级
4 新增阶段零 无 先用 1 个技能低成本验证需求，再投入做工作台
5 引用核验 只要求「可溯源」 新增撤稿状态检查并升为旗舰功能。行业实测：主流模型生成的引用有 78%–90% 是编造的，2025 年全球约产生 14.7 万条虚构引用
6 长任务 只写了「可撤销」 新增「可中断、可恢复」。这是长流程任务的生死线——跑了 20 分钟的任务因网络抖动全没了，用户会直接流失
7 数据安全 本机处理列为 P2 待定 提至 P1。对未发表数据，「能不能不上传」是信任的分水岭，且已有开源项目证明可行
8 成本控制 未提及 新增专节：先筛后做 + 分级使用 + 花费透明
9 差异化判断 「三件事打通」是完全空白 收窄为「有人在做但都还小（1–4 千星），中文生态无赢家」——已有先行者
10 开源合规 未提及 新增第十章：许可证选择、学术署名提醒、数据源条款
11 衡量指标 无引用质量与生态指标 新增引用核验通过率（并对外公开）、技能加载数、技能留存率
12 角色定位 「工作台」 增加第四重身份「技能宿主」，并明确对外口径：AI 是副驾，人才是机长

V1.1 → V1.2（敲定首发技能 + 沙箱选型）

# 改了什么 V1.1 怎么写的 V1.2 为什么改
1 阶段零首发技能定案 「建议做引用真实性核验」，备选投稿前体检 决定已下：引用真实性核验（含撤稿检查）。它是 M2-7 的先行验证版，也最能体现产品定位
2 执行环境架构由一层改两层 把「执行环境」当成一件事 沙箱选型评估发现：桌面端（Windows / macOS）与服务器能用的技术完全不同。必须拆成「云端沙箱层」与「本机执行层」

5 技能安全补两条 5 条要求 新增「凭证不进沙箱」与「出站流量可控」——CubeSandbox 的凭证托管与 eBPF 出站过滤可满足

7 风险表补两条 8 条风险 新增「沙箱方案覆盖不到桌面端」和「沙箱上游仍在 0.x」
8 新增附录 12.4 无 完整的沙箱选型评估报告（实测数据、优势、硬性限制、结论、落地决策）

两个重点候选的细节

① microsandbox —— 本机层的首选

官方定位是「easy, fast, local microVMs for untrusted workloads」，关键特性与我们的需求高度吻合：

它的特性 对应用户的哪条需求
跨平台：Linux / macOS / Windows 解决 V1.2 的"桌面端跑不了"难题
可嵌入：直接在代码里起沙箱，无需部署服务、无常驻进程 不用像 CubeSandbox 那样运维一个服务——对一个没有运维人手的团队，这是决定性的
硬件级隔离（微型虚拟机） 与云端同级的隔离强度
快照与分支：保存运行中状态、随时恢复 对应 5.5 长任务可中断可恢复
密钥永不进入沙箱 对应 5.7「凭证不进沙箱」
平均启动 <100ms 技能频繁起沙箱时不拖慢体验
兼容 OCI 镜像；已提供 Python / TypeScript / Rust / Go SDK 与云端技术栈可复用
自带 Agent Skills 与 MCP server 与我们的"技能宿主"定位天然契合
前置要求：macOS 需 Apple Silicon；Linux 需 KVM；Windows 需 WHP 必须写进安装说明——不满足的用户走降级路径
⚠️ 官方标注为 beta 软件，会有破坏性变更 需锁定版本，并保留降级方案

② sandbox-runtime —— 轻量降级层

Anthropic 为 Claude Code 开源的沙箱运行时，理念是「不需要容器」：macOS 走系统原生沙箱、Linux 走无特权进程隔离，配合基于代理的网络过滤，可限制文件读写、网络访问、本地 socket。

  • 它的价值：安装门槛极低（一条命令），且已在真实产品中承担安全职责。
  • 它的局限：不支持 Windows；隔离强度低于微型虚拟机；官方标注为研究预览版。
  • 适合场景：用户机器不满足硬件虚拟化要求时的降级；或处理"低风险脚本"时的默认档。

本机层建议的降级路径

优先级 条件 采用
1 硬件虚拟化可用 microsandbox（硬件级隔离）
2 macOS / Linux 但不满足条件 1 sandbox-runtime（系统级隔离）
3 都不满足（如 Windows 未开虚拟化） 纯文本模式：不执行脚本，只跑不需要代码的能力

建议：本机执行层的技术风险已经消除（方案明确、均为宽松许可），剩下的只是工程工作量。因此建议由 V1.2 的"阶段二"提前到"阶段一后半段"——因为 5.6 承诺的「敏感数据本机处理」如果没有本机执行能力，实际价值会大打折扣。是否提前，见 12.3 待确认清单。

12.6 技术栈定案：Tauri 外壳 + Python 内核（V1.5 新增）

一、定案内容

层 技术选择 说明
UI 外壳 Tauri（Rust + 系统浏览器内核） 安装包小、内存省；对研究生普遍配置一般的电脑更友好
执行内核 Python（独立进程） 贴合科研生态；通过 Tauri 官方 sidecar 机制嵌入

二、为什么这个组合成立（三条理由）

  1. Python 内核贴合科研生态。 数据处理、文献解析、统计绘图这些环节，成熟库几乎都在 Python；技能生态里的脚本也大量是 Python 写的。内核用 Python，等于直接站在最大的那个生态上。
  2. microsandbox 提供 Python SDK（安装方式为一条 Python 包管理命令）→ 内核可以直接调用沙箱，完全不需要写 Rust。
  3. Tauri 官方文档明确支持这个用法。 官方原文：

「你可能需要嵌入外部可执行文件来为应用添加功能，或免去用户额外安装依赖（例如 Node.js 或 Python）……常见用例是 Python CLI 应用，或用 PyInstaller 打包的 API 服务。」

官方把这个机制称为 sidecar（边车）。也就是说，这不是绕路的土办法，是官方主推的用法之一。

三、落地机制已核实（Tauri sidecar）

环节 做法
打包配置 在 tauri.conf.json 的 bundle.externalBin 中声明内核可执行文件路径
平台适配 可执行文件需带平台后缀（如 -x86_64-unknown-linux-gnu、-aarch64-apple-darwin），一个平台一份
启动方式 Rust 侧 app.shell().sidecar("内核名")；前端侧 Command.sidecar(...)
进程通信 支持读取内核标准输出、写入标准输入 → 可用来做实时进度推送，正好服务 5.5 的「任务可观察」
权限控制 需在外壳能力配置中显式声明允许执行/派生该内核，并可对参数做校验
Python 打包 官方点名的方案是 PyInstaller；Nuitka 是另一条可选路线

四、必须处理好的三件事（本方案真正的难点）

难点 1：两套独立的 Python 环境，绝不能混为一谈 ⚠️

这是整个架构里最容易搞混、也最容易出事的一点：

宿主内核的 Python 沙箱内的 Python
跑在哪 用户电脑上，由外壳启动的普通进程 隔离的微型虚拟机里
干什么 技能加载、文件访问、任务调度、调用沙箱、进度上报 真正执行技能脚本与 AI 生成的代码
信任级别 可信（我们自己写的） 不可信（可能是社区技能里的脚本）
依赖 必须保持轻量 可以是重型（numpy / pandas / matplotlib / 各学科专业库）
能否直接读用户文件 在授权范围内可以 不能，只能通过挂载的目录

一句话纪律：内核负责「调度」，沙箱负责「干活」。任何来自技能或 AI 的代码，一律只能在沙箱里跑。

难点 2：打包体积与稳定性——本方案最大的工程风险

  • 体积风险：Python 运行时本身就有几十 MB；若把 numpy / pandas / matplotlib 也打进宿主内核，安装包可能冲到 150MB 以上，直接吃掉 Tauri 的体积优势——那就白选 Tauri 了。
  • 对策（关键）：宿主内核保持轻量——只带进程管理、通信、网络请求、数据校验这类小依赖；重型科学计算库只存在于沙箱镜像与云端，不进入宿主内核。
  • 稳定性风险：numpy / scipy / matplotlib 这类含 C 扩展的库，用 PyInstaller 打包时容易出现"模块找不到""动态库缺失"，需要专门测试。
  • 对策：尽早做一次「打包可行性验证」（内核 + 一个含科学计算库的沙箱跑通，量一量实际体积），不要等到阶段一末期才发现打不了包。

难点 3：启动速度

Python 冷启动加导入库会拖慢首屏。对策：

  • 外壳先渲染界面，内核在后台并行预热；
  • 内核常驻，避免每次操作都重启；
  • 把「界面可用时间」与「内核就绪时间」分开呈现——界面先出来，用户就不会觉得卡。

五、一条必须守住的纪律：Rust 侧保持"极薄"

外壳的 Rust 代码只做四件事：

  1. 创建窗口；
  2. 启动与守护 Python 内核（sidecar）；
  3. 转发前端与内核之间的通信；
  4. 自动更新、系统托盘等系统集成。

⚠️ 不要把任何业务逻辑写进 Rust。 一旦写进去，「换外壳」和「将来出网页版」这两条路就被堵死了——而这两条路正是我们选择解耦架构的全部意义。

六、落地检查清单

# 检查项 通过标准
1 内核能被 Tauri 正确启动与守护 外壳启动后内核就绪；内核崩溃能被自动拉起
2 前端能与内核双向通信 能收到内核推送的实时进度流
3 内核可被打包成可执行文件 Windows / macOS / Linux 三平台都能打出
4 打包后体积可控 宿主内核不含重型科学计算库，体积在可接受范围内
5 内核能调用沙箱 通过 microsandbox 的 Python SDK 成功起沙箱并拿到结果
6 两套 Python 未混用 代码审查确认：技能脚本与 AI 生成代码只在沙箱中执行
7 Rust 侧足够薄 除上述四件事外，Rust 中无任何业务逻辑
8 统一执行接口可用（V1.6 新增） 同一套用例在本机与云端两种后端上均能跑通；编排层中不存在任何后端专有代码（见 3.3 D2-2）
9 桌面端任务生命周期有效（V1.6 新增） 关闭窗口后任务在后台继续；完全退出后重开能「继续上次任务」；任何中断都显式告知用户（见 5.5）

七、一句话总结

Tauri 管「壳」，Python 管「脑」，microVM 管「手」。 三者各守边界：壳要薄、脑要轻、手要严。
