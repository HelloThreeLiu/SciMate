阅读提示

本报告回答一个问题：PRD V1.5 里的方案，照着做能不能成？ 结论分三个层次给出：哪些立得住、哪些有硬伤、哪些还没想清楚就开工了。每一条判断都标注了 PRD 的具体章节出处，可以直接翻回去核对。

零、三分钟速览

一句话结论：这是一份质量高于平均水平的 PRD——方向对、选型有据、边界清晰；但它目前最大的问题不是"方案错"，而是"排期虚"和"四个发动机级的前置决策还悬着"。照单全收地按第 2–4 个月交付 MVP，大概率延期或砍功能；先补齐前置决策、修一轮一致性，方案本身是可以落地的。

三个最关键的发现

  1. 排期是最大硬伤。 阶段一（第 2–4 个月）实际要交付约 12 条工作流（见 3.3 节盘点表），包括三平台桌面打包、云端沙箱部署运维、技能编排与中断恢复这些各自就需要以月计的硬骨头。「自研 5 件」的说法把「执行环境（文件 + 沙箱 + 网络）」算成 1 件，掩盖了真实工作量。
  2. 四个「发动机级」依赖未拍板，却支撑着 P0。 ① 大模型从哪来（BYOK？代理？支持哪家？）——全文没有一节讲这个，而整个产品靠它驱动；② 云端服务器资源（B 组 #6 未定，但云端沙箱层是 P0）；③ 撤稿数据源（旗舰功能 M2-7 的「撤稿检查」没有点名任何数据来源）；④ 团队人力（PRD 从未说明有几人，12.5 的建议按人手分场景，但全文不知道自己有几人——排期可行性的分母缺失）。
  3. 桌面化定案没有传导全文，其中一处是实质设计缺口而非措辞问题。 5.5 的「用户可关闭页面去做别的事」是网页 + 服务器语境的遗产；桌面应用关掉窗口通常意味着退出整个应用、终止 Python 内核——「长任务可恢复」这条 P0 承诺在桌面形态下反而更难兑现，需要托盘常驻或退出打快照的专门设计，PRD 未提。此外 5.9 还在要求「Chrome / Edge / Safari 兼容」「适配平板浏览器」。

给评审会的一句话建议

不要在这次评审上讨论「方案对不对」——方案大体是对的。要讨论的是四件事：我们有几个人、模型从哪来、服务器谁出、撤稿数据用哪家。这四个答案出来之前，阶段一的任何排期都是假设。

一、评估说明

1.1 评估范围

本评估覆盖 PRD V1.5 全部十二章内容，并参照《科研 Agent 开源生态调研报告》V1.2 交叉验证其中的市场与生态论据。评估针对「方案可行性」，即：按这份文档走，产品能不能在可接受的时间与资源内被做出来、并兑现文档承诺的价值，不针对具体功能设计的优劣做逐条产品评审。

1.2 评估维度

产品定位与市场策略 / 技术架构 / 阶段划分与排期 / 资源与外部依赖 / 合规安全与分发 / 文档内部一致性 / 验证与度量设计，共七个维度。

1.3 数据采信边界（重要声明）

PRD 与调研报告中的第三方项目数据（星标数、许可证、平台支持、性能指标）均标注为 2026-09-16 经 GitHub 官方接口实测。本评估未重新核验外部数据，按文档自述采信；据此做出的技术判断（如「CubeSandbox 依赖 KVM 因而桌面端不可用」「microsandbox 要求 Apple Silicon / WHP」）与文档内部逻辑自洽。建议：在阶段零结束与阶段一中期两个节点，对关键上游项目（CubeSandbox、microsandbox、Tauri sidecar 行为）做一次数据与行为复核——上游均为快速迭代期，评估结论有半衰期。

二、先说结论的前一半：这份 PRD 做对了什么

公平起见，也为了防止评审会把力气花在改对的东西上，先列出立得住、不需要动的部分：

# 做对了什么 出处
1 产品边界清晰：「不做什么」六条写在第一章，学术诚信（不代写、不编造、不替用户下结论）贯穿全文而非点缀 1.4、5.8、M3-7
2 形态决策有据：「工作台 + 技能宿主」避免了与数十个成熟技能正面竞争，五件「技能做不到的事」（课题空间、加载、编排、本机处理、任务恢复）确实是差异所在 1.5、调研报告第十章
3 验证顺序正确：阶段零用 1 个技能低成本验证需求，且明确区分「单个技能有没有人要」和「工作台成不成立」是两件不能互替的事 第七章
4 自我纠错机制罕见地好：V1.3 公开修正 V1.2 的错误结论、保留归档、写明教训（「不能用一个项目的限制否定一条技术路线」）——多数团队做不到这一点 12.1
5 技术选型落到可核验事实：许可证逐条核对、按 E2B 标准写接口层对冲锁定、本机沙箱设计三级降级路径且「不静默降级」 12.4
6 风险表可用：14 条风险每条有具体表现与应对，含三条 V1.5 新增的打包风险；12.6 的 7 条落地检查清单把「能不能落地」变成可勾选项 第九章、12.6
7 架构纪律明确：「两套 Python」「内核保持轻量」「Rust 保持极薄」三条纪律直指这类架构最常见的腐化路径 12.6
8 功能可测试性好：每个功能点带「实现方式（自研/借力/混合）」与验收要点，后续可直接转测试用例 第三章

以上八条建议在后续修订中原样保留，不要因排期压力而放弃其中任何一条（尤其是边界与诚信底线）。

三、分维度评估

3.1 产品定位与市场策略 —— 可行性：高

成立的部分

  • 目标用户（硕士/博士为主）画像具体、痛点真实，五条差异化空白（学科、语言、打通、门槛、诚信）有调研数据支撑，且调研报告自己已经把「完全空白」收窄为「有人在做但都还小、中文生态无赢家」——判断是诚实的。
  • 「能力从生态借，价值由自己做」的策略逻辑自洽：技能生态是上游供应链而非竞争对手，做宿主可以收编生态而非对抗。
  • 阶段零选「引用真实性核验」作为首发技能，判断准确：现有技能几乎无人做、直接命中行业最大痛点（78%–90% 编造率）、且是 M2-7 的先行验证。

保留意见（不构成否决，但要有清醒认识）

# 保留意见 说明
1 阶段零的验证样本有偏 技能形态的用户必然是已经在用 Claude Code / Cursor 的「先进用户」，与主流画像「不写代码的小硕」重合度低。技能受欢迎 ≠ 工作台有需求，PRD 自己也承认这一点（第七章注），但没有设计对冲手段（见 3.7 建议）
2 「宿主能力被平台覆盖」的应对偏软 风险表里这条的应对是「科研专用宿主定位 + 中文场景 + 本机处理」。其中「中文场景」可复制性强，「本机处理」依赖本机沙箱覆盖率（见 3.2 缺口 3）。真正难复制的只有「课题空间 + 三件事打通」——这恰恰是工程量最大的部分，差异化与投入成正比，这是本方案的宿命，不是缺陷
3 商业模式完全未涉及 开源项目可以不做商业化，但 C-5「资源消耗透明」、阶段三「机构版」都隐含了结算与付费口径；模型供给问题（见 3.4）不解决，这条无法设计

小结：定位层面没有方向性错误，可以按此推进。

3.2 技术架构 —— 可行性：中高，有五个缺口

单项选型评估（均按 PRD 自述数据采信）：

技术决策 判断 依据
Tauri 外壳 + Python 内核（sidecar） ✅ 成立 官方文档明确支持 PyInstaller 打包的 Python 服务；PRD 已识别体积与打包稳定性风险并给出对策
云端沙箱 = CubeSandbox + E2B 接口层 ✅ 成立 许可证干净、E2B 兼容可对冲锁定；但 0.x 版本 + 部署条件苛刻（KVM/XFS/root/glibc），运维成本被低估（见缺口 4）
本机沙箱 = microsandbox（+ 三级降级） ✅ 方向成立 跨三平台、Apache-2.0、可嵌入无需运维；beta 状态与硬件门槛已识别。覆盖率问题见缺口 3
两套 Python 纪律 / 内核轻量 / Rust 极薄 ✅ 正确 直指该架构最常见的失败模式，且配了检查清单
「外壳与内核解耦」的可逆架构 ✅ 正确 换壳、出网页版、内核选语言三条路都留着，这是 V1.4 最有价值的决策

五个缺口（按严重程度排序）：

缺口 1（严重）：桌面端「关窗即杀内核」与 5.5 可恢复承诺直接冲突。 5.5 写「用户可关闭页面去做别的事」（5.5 表、2.4 场景五「关掉浏览器」），这句话成立的前提是网页 + 服务器架构——浏览器关了，服务器上的任务还在跑。V1.5 定案桌面应用后，前提没了：Tauri 应用关掉窗口，默认行为是退出进程、连带终止 Python sidecar。要兑现「可中断、可恢复」，必须专门设计以下三者之一（或组合）：最小化到托盘常驻后台 / 退出前自动打检查点 / 内核独立于窗口生命周期存活。PRD 的 Rust 四件职责里提到了「系统托盘」，但没有把它与 5.5 的承诺关联起来。这不是措辞问题，是一条 P0 承诺在架构上还没有着落。

缺口 2（重要）：本机层与云端层没有统一执行接口。 12.4 决策「接口层按 E2B 标准写」只覆盖云端；本机 microsandbox 用的是自己的 SDK。技能编排层（D1-4）将同时面对两种后端——同一个「跑一段脚本」请求，落在本机还是云端、结果如何回传、检查点存在哪，都需要两层各自实现。PRD 没有定义这层抽象，编排层的工程量会因此膨胀。建议定义统一执行接口（起沙箱/执行/取结果/打快照/网络策略），编排层只认接口。

缺口 3（重要）：本机沙箱的覆盖率在目标人群中可能偏低。 microsandbox 要求 macOS 为 Apple Silicon、Windows 开启 WHP、Linux 有 KVM。目标用户是「电脑配置一般」的研究生——高校里 Intel Mac 与未开启虚拟化的 Windows 仍有相当存量（实验室公用机、老笔记本）。这部分用户落入降级路径：sandbox-runtime（不支持 Windows）或纯文本模式。也就是说，相当比例的 Windows 用户只能拿到「不能跑脚本」的降级体验，而「数据不出本机 + 能执行技能」同时成立正是 V1.3 修正的核心卖点。风险表已有此条，但定性为「兼容性覆盖不全」，实际是「核心卖点对部分主力用户不生效」，量级被低估。建议阶段一后半段接入本机层时，先用试用用户做一次硬件条件摸底，把真实覆盖率量出来再决定宣传口径。

缺口 4（重要）：分发工程完全缺失。 全文检索「签名 / 公证 / 杀软 / 误报」零命中。现实是：PyInstaller 产物是杀毒软件误报与 Windows SmartScreen 拦截的重灾区；macOS 需要 Apple 开发者账号与公证，否则用户首次打开即被 Gatekeeper 拦截；Rust 职责里提了「自动更新」但无更新通道方案。对一个「靠研究生口口相传安装」的产品，装不上比功能少更致命。这一项有真金白银的成本（代码签名证书、开发者账号），应进排期与预算。

缺口 5（中等）：沙箱镜像分发与预热的体验未评估。 「重型科学计算库只存在于沙箱镜像与云端」守住了安装包体积，但代价转移到运行时：用户首次跑一个数据技能，需要拉取含 numpy/pandas/matplotlib 甚至 R 环境的镜像——数百 MB 的下载对「配置一般 + 校园网」的用户是一次性劝退点。需要设计镜像预下载、精简分层、常用镜像预置等机制，PRD 未提。

小结：架构没有选错的东西，五个缺口里四个是「没写到」而非「写错了」，均可补。缺口 1 必须在阶段一开发前补上设计。

3.3 阶段划分与排期 —— 可行性：中低（全文最大风险点）

阶段一真实工作量盘点（把「自研 5 件」拆开到可估算粒度）：

# 实际要交付的内容 对应条目 工程量评估
1 Tauri 外壳（三平台）+ Python 内核 + sidecar 集成 + PyInstaller 三平台打包 12.6 中—高（PRD 自认的最大工程风险）
2 课题空间：存储模型、界面、导入导出 C-1 中
3 技能加载器 + 渐进式加载（双目录兼容） D1-1 / D1-2 中
4 技能编排 + 中断恢复状态机 + 检查点 D1-4 / C-2 高（含缺口 1/2 的设计）
5 文件授权系统（授权 UI、记录、回收） D2-1 / D2-5 中
6 云端沙箱层：服务器准备（KVM/XFS/glibc）+ CubeSandbox 部署 + E2B 接口层 + 持续运维 D2-2 中—高（依赖 B 组 #6 拍板）
7 网络白名单（eBPF 出站过滤配置） D2-3 低—中
8 旗舰功能：引用真实性核验 + 撤稿检查（含数据源接入） M2-7 中（依赖撤稿数据源拍板）
9 自研功能 4 项：数据清洗、结果解读、段落写作、学术诚信提示 阶段一表 中
10 借用技能 4 项的集成与适配（检索/绘图/引用格式/排版） M2-1 / M1-4 / M2-5 / M3-5 中（隐含兼容问题，见 3.4 依赖时序）
11 （计划中）本机执行层 + 三级降级路径 3.3 表格 高（若并入阶段一后半段）
12 试用运营：30–50 人招募、反馈收集、指标统计 阶段一成功标准 中

判断：12 条工作流、3 个月。按软件工程的常规产出估算：

  • 2–3 人团队：不可行。 光 #1（三平台打包）+ #4（编排与恢复）+ #6（沙箱部署运维）三项就超出 3 个月容量。
  • 4–6 人团队且打包验证一次通过：勉强可行，无缓冲。 任何一项 PRD 自己列出的风险（打包异常、沙箱 0.x 的 API 变更、microsandbox 破坏性变更）触发，即延期。
  • 里程碑「第 4 个月 MVP 上线试运行」与阶段一成功标准（30–50 人完成完整任务）之间还压缩了招募与试运行周期。

其他排期问题：

# 问题 说明
1 打包可行性验证没有排期 12.3 B 组 #4 自己说这是「新的最优先项」，但全文没有给它负责人和截止日期——最优先的事不在里程碑表里，等于没有排期
2 阶段三「第 12 个月机构版落地」过于乐观 高校/机构的采购与合作流程本身常以半年计；从「协作能力上线」（第 9 个月）到「机构版落地」（第 12 个月）只有 3 个月，建议把里程碑改为「首批机构合作意向/POC」
3 阶段零 1 个月偏紧但可接受 发布 1 个技能 + 收集反馈在 1 个月内可行，前提是撤稿数据源申请（若有批量访问门槛）立即启动——这类申请的审批周期不受我们控制

小结：范围切分（阶段零先行、自研/借用分层）的结构是对的，问题出在日历上。调整方案见 5.4。

3.4 资源与外部依赖 —— 可行性：不明朗

这是本 PRD 最隐蔽的一类问题：四个支撑着 P0 功能的前置依赖，至今没有答案。

# 未决依赖 影响的 P0 现状
1 大模型供给：用户用谁的模型？BYOK（用户自带 Key）还是产品代理？支持哪些供应商？国内可访问性与网络条件？密钥如何本地存储加密？ 全部功能 完全未提及。 全文与「模型/Key」相关的只有 5.7「技能调用外部服务的凭证托管」——那是技能的 Key，不是产品自身的发动机。5.3 成本控制三条原则、C-5 资源消耗透明，都悬空在没有供给方案的天上
2 云服务器资源与运维归属 D2-2 云端沙箱层（P0） 12.3 B 组 #6 未拍板。CubeSandbox 的部署条件（KVM/XFS/root/glibc≥2.31）已查明，但「谁来出服务器、谁来运维」没有答案，而它挡在阶段一的必经之路上
3 撤稿数据源 M2-7 引用真实性核验（旗舰，P0） 全文未点名任何撤稿数据来源（Retraction Watch 数据库的批量访问通常需申请、Crossref 撤稿元数据有频控约定）。阶段零就要做这个技能，数据源可得性应在阶段零第一周验证
4 团队人力 全部排期 PRD 从未写明团队规模与构成。12.5 的选型建议按「团队能否接受少量 Rust / 只有前端人手」分场景——但文档没有说自己属于哪种。没有这个数字，第七章所有时间表都无法评估可行性

一个依赖时序问题：D1-6「兼容性降级提示」排在阶段二，但阶段一就要「借用技能」——社区技能依赖特定客户端专有能力（Claude Code 的 Task/Agent、allowed-tools 等），兼容问题在阶段一第一个月就会遇到。至少应把 D1-6 中「加载时检测」的部分提前到阶段一，否则阶段一的借用技能会以「静默失效」的方式消耗试用用户的信任。

小结：这四项不解决，PRD 的任何排期都是假设。它们应该成为评审会的第一议题，排在所有功能讨论之前。

3.5 合规、安全与分发 —— 可行性：中

覆盖较好的部分：

  • 技能安全体系完整：不预装、装前透明、显式授权、沙箱隔离、版本锁定、凭证不进沙箱、出站可控（5.7）——这套设计明显吸收了「浏览器 vs 扩展」的成熟经验。
  • 开源许可证纪律严格：仓库级与文件级许可证区分、CC BY-NC / AGPL 红线、第三方清单制度（第六、十章）。
  • 学术诚信贯穿：AI 内容标识、不提供代写入口、提示机构规定（5.8、M3-7）。

缺口：

# 缺口 说明
1 数据流向未图示 产品是「本地优先 + 云端沙箱」的混合形态：哪些数据、在什么模式下、经什么路径离开用户电脑（提示词发给模型厂商？文件上传云端沙箱？），没有一张图说清。5.6 的原则都对，但「敏感数据本机处理」的边界（本机模式下提示词是否仍发给云端模型？）直接决定这条承诺的真伪——如果本机模式下用户数据仍需发给模型 API，那「数据不出本机」的说法需要重新措辞
2 生成式 AI 合规未评估 若产品提供任何模型代理/网关（阶段一的云端层 + 可能的模型路由），需评估《生成式人工智能服务管理暂行办法》等规定的适用性；纯 BYOK 桌面工具风险较低，但这个判断本身需要写下来
3 5.6 的「账号」概念与桌面形态错位 「一键彻底删除账号与内容」「不同用户之间严格隔离」是多租户云服务的语言，桌面本地应用没有定义过账号体系。要么删掉，要么说明何时引入账号（云同步？机构版？）
4 分发合规 即 3.2 缺口 4：签名、公证、杀软误报、更新通道，涉及预算与周期，需进排期
5 数据源条款核查未落实到项 10.3 有原则性提醒，但 M2-1（P0）上线前应完成对具体接入源（arXiv / OpenAlex / Semantic Scholar / Crossref / PubMed）逐家的频控、署名、商用条款核查并留档

3.7 验证与度量设计 —— 可行性：中高

成立的部分：四个阶段都有可量化的成功标准；阶段成功标准（60% 完成率、70% 省时感、<5% 错误反馈）定得务实；「引用核验通过率对外公开」是有魄力的承诺。

三点改进建议：

# 建议 理由
1 精确定义「引用核验通过率 ≥98%」的分母与口径 若分母是「所有核验过的引用」，那么把可疑条目标为「未能核实」并不拉低通过率——指标可被保守标注稀释。建议拆成两个：可核实引用中确认真实的比例 + 标注「未能核实」的比例（后者本身也是质量信号）
2 阶段零增加转化意愿度量 光有「≥10 条有效反馈」不够。加一条：技能用户中愿意留下联系方式等待工作台试用（waitlist）的比例——这是把阶段零的先进用户变成阶段一种子用户的通道，也部分对冲 3.1 保留意见 1 的样本偏差
3 补充试用用户招募方案 30–50 名目标用户从哪来（课题组？高校社群？阶段零 waitlist？）、如何筛选（学科分布、电脑条件——顺带完成 3.2 缺口 3 的硬件摸底），需要一段文字，否则阶段一成功标准无法执行

5.4 排期调整：三个可选方案

方案 做法 适合 代价
A · 保决策、放宽排期 阶段一延长至 4.5–5 个月（里程碑顺延），其余决策不动 团队 ≥4 人、有服务器与运维资源 整体上线推迟 1–2 个月；对科研用户，暑假/寒假窗口值得考虑

六、最终结论

方案可行，排期不可行，四个前置决策必须先落。

具体地：

  1. 方向与定位：可行。 差异化判断诚实、边界清晰、诚信底线贯穿，生态策略（做宿主不做竞争者）逻辑成立。
  2. 技术架构：基本可行。 Tauri + Python 内核 + 双沙箱层的选型每一项都有核实依据；五个缺口（桌面长任务生命周期、统一执行接口、本机覆盖率、分发、镜像体验）都是「没写到」而非「写错了」，可以补——但缺口 1 必须在阶段一开发前补上设计。
  3. 排期：按当前文档不可行。 阶段一约 12 条工作流对 3 个月，只有 4–6 人团队且风险全不触发才勉强成立。需按 5.4 调整。
  4. 前置决策：四项未拍板（模型供给、服务器、撤稿数据源、团队人力），且第一项不在任何待确认清单里。 它们应成为评审会的第一议题。
  5. 文档质量：高，但需一次「桌面化传导修订」（7 处）。 其中 3.3 节内的自相矛盾与 12.2 统计失真应在下一版清理。

最后说明一点：这份 PRD 最宝贵的部分，是它把「我们错过在哪里」公开写进了版本史（V1.3 对 V1.2 的修正与教训）。本报告沿用了同一标准——结论可以被推翻，但依据要留痕。若评审会对本报告的某条判断有异议，欢迎用同样的方式指出：给出具体章节与事实，我们把它修回来。
